UX Review · Local Add-on · August 2026

Nexus AI feels sprawling because it is organized around itself

Read against 14 screenshots and the local-addon-nexus-ai source. Four structural problems, seventeen findings, a proposed information architecture, and a sequence to get there.

The short version

Nexus is built around its subsystems — indexers, sync jobs, credential stores, an MCP server, a proxy, five agents — and the UI is a faithful map of that architecture. But a user has two jobs: ask questions about their fleet, and decide on what the agents found. Neither has a home. Both are scattered across six tabs, three chat surfaces, two settings pages, and a floating button.

The sprawl is not primarily a visual-density problem. Cutting cards and tightening spacing would leave the same app. The fix is to decide what Nexus is for, promote those two jobs to the top level, and demote everything else — ports, token counts, index progress, sync intervals — to places you visit when something is wrong.

Five front doors, each with its own model of the product. A new user has no way to learn which one to open, and the app never tells them — except once, on Ask/Tell, where it recommends leaving for the CLI.

Problem A

Too many front doors, and the good one is hidden

The same capability is reachable three or four different ways, at three or four different qualities. Users pick whichever one they stumble into first, which is rarely the best one.

01

Three chat surfaces, and the product apologizes for one of them

There is an "Ask Nexus AI" box on Dashboard, an Ask/Tell tab, and the docked panel. The docked panel is clearly the real product — session history, context selector, rich formatted answers, follows you across tabs. Ask/Tell is an empty box under a banner that reads "Ask/Tell is a quick way to try Nexus AI. For a richer experience with full tool support, use the MCP server or CLI." A tab whose own copy says to go use something else should not be a tab.

Ask/Tell — an empty tab that recommends the CLI
The docked panel — the actual product, behind a floating button
Fix: delete Ask/Tell and the dashboard prompt box. Promote the docked panel to a first-class destination that can also open full-width. One chat, one history, one quality bar.
02

Settings has two homes that each know about the other

Preferences → Nexus AI holds AI provider, gateway, WPE credentials, AWS S3, connected accounts, chat history, external SSH hosts. Dashboard → Settings holds auto-indexing, sync schedule, WPE access & permissions. Neither is a subset of the other, and the code shows the seam: the Settings tab renders "Manage in Preferences → Nexus AI" as a hint, and SettingsTab.tsx keeps state "not just in NexusPreferences" so its permissions section can render. Access & Permissions appears in both.

Preferences → Nexus AI
Dashboard → Settings
Fix: one home. Everything configuration-shaped goes to Preferences → Nexus AI; the Settings tab disappears. If a setting is needed in flow, surface it as a link back, never as a second copy.
03

Six background jobs, each configured independently, none priced

Content index interval, offline site scan, metadata sync, site info updates, content index for WPE — five checkbox-plus-hours rows, plus per-agent schedules, plus a Schedule button on Dashboard. The real cost is buried in body copy: "Opens one SSH connection per install," "Also uses one SSH connection per install," "no extra connection cost." At 333 installs those sentences are the whole decision, and nobody reads them.

Fix: one "Background work" page with a master switch and a plain-language consequence per row — "≈333 SSH connections every 4 hours, last run took 11 min." Make the cost the value in the row, not a sentence under it.
04

Naming assumes the reader built the system

Ask/Tell, Preflight, Local Twins, Deep Scan Scope, Fleet Intelligence, Data Completeness, Auto One-Click Admin, Nexus itself. Several are internal shorthand promoted to UI labels. "Ask/Tell" in particular is a distinction only the implementer cares about — the user just talks to it.

Fix: rename to what the user would say. Ask, Sites, Agents, Inbox. Reserve invented nouns for things that genuinely have no plain name.
Problem B

The dashboard reports on the software, not the fleet

The landing surface answers "is Nexus working?" A user opens it wanting to know "is anything wrong with my 367 sites?"

05

The first screen is an install log

Above the fold: a prompt box, a terminal command to paste into Claude Code, MCP server port 10801, 201 tools, v0.1.0. Then three progress bars, a WordPress-version histogram, two "Running" service cards with port numbers, and a gateway cost readout showing $0.0000. Setup instructions and process health are permanent furniture on the most-visited screen. Nothing here changes what the user does next.

Dashboard, above the fold — MCP setup commands and port numbers
Fix: move connection instructions into a one-time setup flow plus a Preferences page. Move service health into a single status line that turns red when it isn't green. Give the space back to what needs a human.
06

The site counts do not reconcile — this is the biggest trust problem in the set

Across four screens the same fleet is described as: 367 sites (37 local · 330 WPE); Remote Sites 330 with "29 linked · 301 not linked"; WPE-connected 19; Data Completeness 370/370; WP Engine 333 installs; "11 of 14 accounts"; and Agents settings "11 accounts". Six different totals. Some of these are legitimately different quantities, but the UI gives no way to tell which — so the reasonable conclusion is that the numbers are unreliable, which poisons everything else on the page.

370/370 and 367 sites, same screen
333 installs, 11 of 14 accounts
Fix: define one canonical fleet count and one canonical scope, compute both in one place, and render them identically everywhere. Where a number is scoped differently, say so in the label ("333 installs in 11 included accounts"), never silently.
07

Six vocabularies for one idea

"How much does Nexus know about this site?" is expressed as Scanned / Configured / Searchable, as indexed / metadata / filesystem, as fresh / stale, as synced / needs SSH sync, as a three-dot meter, and as a percentage bar. They overlap but do not map cleanly onto each other, so no amount of use builds a model.

Fix: one ladder, one name, three rungs — Basic → Detailed → Searchable — with freshness as a separate timestamp, not a second vocabulary. Use the same three words in the site table, the fleet summary, and the agent scope picker.
08

Big numbers spent on small facts

Activity leads with three hero cards: 104 total events, 0 today, All Systems Healthy. The largest type on the screen is a zero. Meanwhile "31 actions need your review" — the only number that implies work — is a banner on a different tab.

Fix: size type by consequence. Pending reviews and failing agents get the hero treatment; lifetime event counts get a caption.
Problem C

Nothing is triaged, so everything looks equally urgent

Lists are rendered in arrival order at uniform weight. The app has plenty of signal about what matters and uses none of it to sort.

09

"All Systems Healthy" while an agent fails every twenty minutes

The Activity tab shows a green "All Systems Healthy" and a Top Issues panel with a checkmark and "No issues detected." On the Agents tab at the same moment: security-sentinel has a red last-status, 17 items need review, and its activity log shows five identical failures between 15:17 and 18:00. Health is being computed from the wrong inputs, and a health indicator that can be confidently wrong is worse than none.

Activity: no issues detected
Same period: five consecutive sweep failures
Fix: health rolls up agent run status, stale syncs, and credential failures. If any input is unknown, say "unknown" rather than green.
10

Errors are printed, not handled

One entry is a 500-character shell command with absolute paths and inline PHP. Four others read "(s.evidence || []).map is not a function" — an internal type error shown verbatim to the user, four times, with no aggregation, no cause, no action. A row labelled "sweep complete" says "No summary available." The log is a transcript of the implementation rather than an account of what happened.

Fix: collapse repeats into one row — "Sweep failed 5× since 15:17" — with a plain-language cause, a Retry, a Mute, and raw detail behind a disclosure. Auto-pause an agent after N consecutive identical failures and raise it to the inbox.
11

Approval debt is a badge, not a place

31 pending decisions are announced in a banner on Agents, split as 17 on one agent's sub-tab and the rest elsewhere. Reviewing agent proposals is plausibly the single most frequent recurring task in this product, and it has no destination — you reach it through two levels of tab.

The review queue as a banner above five agent cards
Fix: make Inbox the first destination and the default landing view, aggregating approvals, findings, and failures across all agents. Badge it in Local's left rail so it is visible without opening Nexus.
12

Operations is 37 identical rows and four equally-weighted buttons

Every row reads "halted · Searchable · 7h ago." Nothing is sorted by staleness or by problem, so scanning is pointless and the only usable interaction is expanding a row you already knew to look for. Above it, four full-width teal buttons compete at identical weight, and an empty Bulk Operations panel occupies roughly 200px to say "No bulk operations yet."

Twenty-three rows of the same three facts
Fix: fold this into a single Sites table — sortable, filterable, searchable, with selection. Operations become actions on a selection rather than a separate tab, which also removes the "which list am I in" problem between Dashboard, Operations, and agent scope pickers.
13

The event timeline is mostly auto-drafts and the word UNKNOWN

Seven of eight visible rows are auto-draft creation and deletion, every one tagged UNKNOWN. This is WordPress background churn, recorded faithfully and surfaced at full weight. It teaches users that the timeline is not worth reading.

Fix: filter auto-drafts and revisions by default. If actor is unresolvable, omit the field rather than print UNKNOWN.
Problem D

Craft debt that makes it feel heavier than it is

14

One column at 1500px

Every screen is a stack of full-width white cards. Settings rows put a label at x=140 and its control at x=1450, with a thousand pixels of nothing between them — the checkbox and the thing it controls are as far apart as the layout allows. Buttons stretch to 700px. The eye has no anchor and the page reads as endless.

Fix: cap content at ~1100px, size buttons to their labels, and keep a control within a few hundred pixels of its label.
15

Two visual systems in one product

The docked chat is dark with cyan accents; the dashboard is white with teal; the agent workspace uses a third, deeper teal with pill buttons; Preferences uses Local's native grey chrome. Four looks, reachable within two clicks of each other.

Fix: adopt Local's chrome everywhere and keep exactly one accent. The chat panel should follow the app's light/dark setting, not impose its own.
16

Empty states are dead ends

"No bulk operations yet." "No AI requests in this time period." "No summary available." "Last run: Never run" on two of five agents. Each is a large reserved area that states a negative and offers nothing.

Fix: either collapse the panel entirely, or make the empty state the invitation — a never-run agent should show "Run now" as its primary content.
17

Four levels of nesting inside one tab

Dashboard tab → Agents → an agent → Settings/Approvals/Activity/Tools/Docs → an approval drawer. The only wayfinding is a small "‹ All agents" link, and the outer tab bar stays highlighted on "Agents" the whole time so the header never tells you where you are. Each tab keeps its own scroll position, so returning to Operations drops you mid-list.

Fix: a real breadcrumb at every depth, and reset scroll to top on tab entry unless the user is returning from a detail view.
After your answers

Three of your answers change the diagnosis

Everything above still holds, but the target user you described makes two of the problems much larger and one of them smaller.

A

Content strategists and marketing PMs cannot read this product today

If the vision is the tool for non-developers managing sites, the current surface is the wrong language nearly everywhere. On the four most-visited screens a non-dev encounters: an MCP server port, a claude mcp add terminal command, "201 tools available", "77 unknown (need SSH sync)", "Opens one SSH connection per install", a vector database size in megabytes, a raw wp-cli invocation with absolute paths, and a JavaScript type error. None of these are things a marketing PM can act on, and several are the largest text on their screen.

This is bigger than renaming, and — since you don't want a dual mode — it has to be settled in the single surface rather than gated behind a toggle. That is the harder and better answer: anything requiring a mental model of SSH, CLI, indexes, embeddings, or ports either gets translated into consequences a non-developer can act on, or it leaves the main surface entirely for Preferences → Advanced. "77 unknown (need SSH sync)" becomes "77 sites we haven't looked inside yet — Sync now." Port numbers and tool counts become one health line. A vector database size becomes nothing at all.

The test for each item is whether a developer would miss it. Most of this material is reassurance that the machinery is running, not something anyone acts on — which is why one surface can serve both audiences without a mode.

Test for it: take any screen and ask whether a web PM could explain, in one sentence, what it is telling them and what they should do. Dashboard, Operations, and Activity all fail that test right now.
B

"Lightweight path" and "THE tool for non-devs" are different products

A lightweight path can afford to be a text box that hands off to the CLI when things get real. The tool for non-devs cannot hand off to anything — chat is the entire interface, because it is the only surface where a content strategist can express intent without learning the fleet vocabulary. That hedge is precisely what produced three chat surfaces of three different qualities.

If you commit to the non-dev vision, chat needs what the docked panel doesn't have yet: suggested openers grounded in that user's actual fleet, results rendered as UI rather than markdown tables, and every action shown as a preview with an undo before it runs. Right now a good answer is a wall of prose the user has to re-read to act on.

Landing rule: open on Inbox when anything is waiting on a decision, otherwise open on Ask. Agency operators will nearly always land on Inbox; a marketing PM with no pending approvals lands where they can just ask.
C

If Dashboard is a health check, it is a pill — not a tab

"Is this thing working?" is one bit of information, checked often and briefly. It currently costs a full tab, roughly three screens of scroll, and it answers the question wrong — Activity says all systems healthy while an agent fails hourly. A question asked that often deserves a persistent indicator in the header: green with a timestamp, red with the one thing that's broken and a way to fix it. Click it for the port numbers and service versions.

This also makes the fix for finding 09 non-optional. A health pill that can be confidently wrong is worse than the current tab, because people will stop opening the tab and start trusting the pill.

D

First run, for someone with 300 sites and no terminal

You named first-time users with lots of sites as a target, and the current first-run experience is a dashboard whose most prominent content is a command to paste into a terminal, above three progress bars that will read 0%. Nothing invites the first useful action, and the initial sync across hundreds of installs is invisible work that takes real time.

Fix: a first-run that connects accounts, shows the fleet appearing as it syncs, and ends on one answered question about their own sites. Defer every agent, credential, and schedule until after that moment.
E

On the six site counts: "not sure" is the finding

If the person who built it can't say from the screenshots whether 367, 370, 333, 330, 29, and 19 are consistent, no user can. Worth an hour: write down what each number is scoped to, find which ones disagree, and put the definition in the label.

The vision frames

Four ideas worth taking now, three worth resisting

Read carefully, the mockups are not a redesigned Nexus. They are a redesigned Local, with Nexus dissolved into it — new top-level nav, a new object model, a persistent assistant panel. That is a much larger commitment than fixing the add-on, and you said you are not looking to do all of it. The useful move is to separate the ideas from the scope.

Take it — highest value, smallest blast radius

The right-hand Insights / Chat panel

One panel, two tabs, always present, contextual to whatever is on screen. It resolves three separate findings at once: it is the single chat surface (finding 01), it is the health pill with somewhere to expand into (finding 05 and C), and Insights — broken links, server errors, the publishing checklist, an agent finding with a Review → — is the Inbox, delivered where the user already is instead of as a tab they must remember to open. Almost everything it displays already exists in Nexus. This is mostly repackaging, and I would build it before anything else.

Take it

Agents become Workflows, named by outcome and grouped by goal

"Automations and agents that do real work on your site. Pick one and run it," then For Content / For Performance / For Search / For Security, each card one sentence and one button. Compare with today: five agents named after their mechanism, each opening into five sub-tabs of autonomy levels, event triggers, and site scope. A content strategist can choose "Redirect Manager" from its description. Nobody outside the team can choose "security-sentinel" with an autonomy level of Suggest only.

The detail page is the other half of it: two configuration fields on the left, a numbered "What it does" on the right. That five-line list is better documentation than the Docs sub-tab, and it is what makes running an unfamiliar automation feel safe. Today's configuration doesn't have to disappear — put it behind an Advanced link.

Take it

Approvals as inline numbered cards, not a queue

"Add 'is best' here to aid organic SEO/AEO — 1 of 2" with Approve / Deny / Skip / Chat, while the affected text is highlighted in the editor beside it. The decision arrives with its evidence attached and costs one keystroke. That is the right answer to 31 pending actions: not a better-organized backlog, but a delivery mechanism that keeps the backlog from forming. It also directly answers your first reply — agents belong, and this is how they belong for a non-developer.

Take it

Runs shown as a live checklist, in plain language

Connected to Google Drive ✓ · Read the doc ✓ · Generating WordPress draft, 2,847 words imported · Detect categories & tags · Create Asana task. Five lines anyone can read, with a Cancel. Set that against the current activity log's 500-character shell command. Same underlying events, opposite legibility. Adopting this format alone fixes most of finding 10.

Careful — the gap

There are four sites in every frame. Your user has 367.

Home lists sites as four cards across the top. Projects lists four in a sidebar. The chat asks "Which site is this for?" and offers a list of four. None of this survives contact with an agency fleet — there is no table, no filter, no search, no selection, no bulk action, no notion of a site you have never opened. You named agency customers with 300+ installs as target one, and this vision currently has no answer for them. That is the biggest thing to resolve before these frames become the plan, and it is exactly where the Sites table from the previous section slots in.

Careful — the risk

The assistant commits real changes on a client's live site

Across these frames chat creates a WordPress post, edits body copy, adds schema, writes an Nginx deny rule, schedules a publish for 9am, posts to a client's Slack, and emails a client for approval. The instincts are good — "Block it. Stage it first," then "Staged ✓ ... Test it, then I'll push to prod." But that safety is currently a property of how the conversation happened to go, not of the system. For a marketing PM operating on a client site, staging and revert have to be structural: every write produces a staged diff, the panel always shows what is staged versus live, and one control reverts it. Get that right and the non-dev vision is defensible. Leave it conversational and one bad turn ends the pilot.

Careful — the regression

The agent picker puts the mechanism back in the composer

Under the message box: Auto · Content · SEO · Site health · Orchestrator · Page builder · Search Visibility. Choosing correctly requires knowing how the system is decomposed — the same demand today's UI makes, relocated. If Auto works, show only Auto and let the panel state which specialist answered after the fact ("Switched to Productivity agent" already does this well). If Auto doesn't work reliably, that is a routing problem to solve rather than a menu to expose.

Two smaller notes in the same spirit: a running workflow appears as a checklist in one frame and as chat messages in another — pick one representation. And Blueprints and Add-ons don't explain themselves from these frames; a nav item whose meaning isn't obvious costs more than it saves.

The decision underneath all of it

These frames and today's Nexus disagree about who owns the surface. In the vision, Nexus disappears into Local as a panel and a nav item — there is no Nexus dashboard at all. Today it is a destination you visit. Both are defensible; you cannot build toward both. Deciding it determines whether the next six months is an add-on that gets simpler or a product direction for Local, and every question below it — where settings live, whether the health check is a tab or a pill, whether agents are configured or picked — falls out of that one answer.

Four destinations, ordered by how often a person needs them. Everything removed from the top level still exists — it moves to where it is relevant, or to Preferences.

Sequence

FirstStop the bleeding — days, not weeks
Fix the health calculation so it accounts for agent failures. Aggregate repeated errors and hide raw commands behind a disclosure. Delete Ask/Tell. Filter auto-drafts out of the timeline. Sort Operations by what is stale or failing. Put the pending-review count on the rail icon.
ThenOne vocabulary, one number
Collapse the six knowledge vocabularies to Basic / Detailed / Searchable. Define the canonical fleet count and scope once and render it identically everywhere. This is mostly naming and a shared selector, and it unblocks everything after it.
ThenBuild the Inbox and the Sites table
The two real destinations. Inbox absorbs approvals and failures; Sites absorbs Operations and the fleet cards. Once both exist, Dashboard, Operations, and Activity can be retired rather than redesigned.
LastUnify settings and chrome
Merge the two settings homes, build the Background work page with real cost estimates, and bring the docked panel onto Local's theme.
Reading the vision inWhere the mockups fit this sequence
The Insights / Chat panel replaces the "then" step above — build the panel rather than a separate Inbox destination, and Inbox becomes its Insights tab. Renaming Agents to Workflows and adding the one-line "what it does" is cheap and can ride along with the first step. Inline approval cards and the run checklist land with the panel. Everything else in those frames — the Local nav, Projects, Blueprints, Live Link sharing, the org switcher — is a separate decision, and none of the above depends on it.
