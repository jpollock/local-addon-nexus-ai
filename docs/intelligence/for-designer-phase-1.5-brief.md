## 1 · The boundary, redrawn in your favor

The four-phase plan gated "the shell inversion" on product buy-in. That
gate applies to LOCAL'S shell — the rail, the Sites matrix, the main
window. It does NOT apply to the Docked Panel's internal IA, which is
the addon's own surface end to end. Nothing gates rebuilding the
panel's inside to your session idiom now. Phase 1.5, inserted between
the ruled phases: **the panel becomes a session.**

## 2 · What we're asking for

The docked run view. When a strict procedure arms in the panel, the
experience should become a RUN, not a chat with attachments:

- **RB-C is your starting shape.** You built "docked run panel,"
  compared it against RB-A/A2/B, and set it aside when RB-A2 won — for
  the full shell. For THIS container, RB-C was always the native
  answer. Revisit it against the seam that now exists (the three stream
  events, the approval card, `procedureView.ts`'s derivations — all
  real, all shipped).
- The transcript framing: a session with consequence (your sessions-
  sorted-by-consequence insight, applied inside one panel) — where does
  the declared block LIVE (sticky? pinned? collapsing header?), where
  do turns go while a run is active, what happens to the block when the
  run finishes (your one-row fold, in a dock).
- The approval card's place in that run view — it now carries the
  derived platform-can't-verify line ("The runbook asks for cp.dry-run —
  show what would change… read the plan above before you approve"), and
  the canary-policy choice with pause labelled as the default.

Constraints that stand: panel width is what it is; the site-context
strip and content-age chip stay; Controlled Vocabulary v1.1 governs;
every count and verdict derived, never authored — your own rule, now
enforced by the seam.
