Where
Why “where” is its own control: the segment partitions on origin — every property originates in exactly one of these, so the counts sum to the total. The state filters below are predicates and compose with the segment (“WP Engine · Needs you”, “WP Engine · Has a copy here”). Corrected from v2, per the designer’s pushback: v2 defined “This machine” as origin-plus-copies, which double-counted 20 WP Engine properties while this note claimed “exactly once.” Presence-on-this-machine is a predicate, not an origin — it lives in the “Has a copy here” chip, and Local’s sidebar-shaped view of your machine is the composition “Everywhere · Has a copy here,” whose count is stated in the header card.
Why search spans everything: a site missing from a filtered view must be explained, never absent — the log-processor Sites-tab ruling, reused. Searching while a filter is active searches the whole fleet and labels rows that fall outside the filter.

Why most rows have no caret: 74% of real properties are a single place. A caret on a row with nothing under it is a lie the user pays for with a click — single-place rows put the place inline and go straight to it. The expansion affordance appears only where there is something to expand. And the roll-up says what it is: a multi-place row’s age reads oldest 12h — the set minimum, labelled — because an unlabelled date claims a freshness no single place has. (v2 silently showed the newest place’s age, which was worse than unlabelled: it claimed a freshness only the best-checked place had.)

What this screen is: the property — the logical thing that exists in more than one place. Nothing executes here; every card is a door to a place, and the lineage below is stated only where a recorded link exists. In the real ledger today: 20 copy links, 2 content-pull links, out of ~296 properties — so stated absence is this screen’s common case, and it is written as a fact with a reason, never as an empty div.
