Remote reach & permissions — thinking the feature through

The screen conflates two independent things, which is why "does this cover external hosts?" was hard to answer. Account scope decides who Nexus contacts on a timer. Operation permissions decide what may be done when someone asks. They live in one card, and the scope label claims to control the permissions. It does not.

Pre-existing bug, independent of external hosts. The scope row says "click to include / exclude accounts from the permissions below". It does no such thing. wpeAccountFilter has exactly two consumers in the main process — WpeRefreshScheduler's getAccountFilter (index.ts:845) and the manual sync (wpe-sync.ts:49) — and isOperationAllowed contains no mention of an account at all. Deselecting an account stops syncing it. It revokes nothing. A user who unticks Golden Ecomm believing they have removed write access to its production installs still has it.

Toggle to compare. The proposed view separates the two axes and adds external hosts to each.

The external schedule is a product decision, mocked as off-by-default rather than assumed. WpeRefreshScheduler iterates installs with a remote_install_id, so external hosts are never refreshed today and always show whatever the last on-demand command found. Defaulting to off keeps that behaviour while making it visible and opt-in — Nexus reaching into somebody's VPS on a 4-hour timer is a different proposition from reaching into a WP Engine install you already administer.

Operation rows52 — wpcli_read, wpcli Scope-chip; dim the three with no external equivalent.

1. Account scope is mislabelled — fix regardless of external hosts. It gates syncing, not permissions. Either move it to Axis A as mocked, or relabel it in place. What it must not keep saying is "exclude accounts from the permissions below", because someone will rely on that.
2. Target exceptions cannot name an SSH host. The only functional bug in Axis B. SettingsTab.tsx:231 writes { installName, environment, overrides } with no targetRef, and the matcher computes e.targetRef ?? `wpe:${e.installName}` — so a UI-made exception is always wpe:-prefixed and can never match ssh:<alias>. The matcher already honours targetRef; the picker just needs to send one, and to list registered aliases beside installs.
3. Scope-chip the operation rows, dim rather than hide. Only Read and Write apply to an ssh: target. Pull, Push and Delete/Promote are WPE platform operations — but they remain real settings for WP Engine, so making them vanish would be worse than marking them.
4. Write the remote* setting keys. The backend was renamed in Plan A; SettingsTab.tsx still writes wpeOperationPermissions and the gate works only because isOperationAllowed falls back to the legacy key. Write the new names, keep reading both, and existing installs migrate silently.
