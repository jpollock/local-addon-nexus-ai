## P1-2 — ESLint config + gitleaks (CI + pre-commit) + release secret-scan

**Labels:** `tooling` `high` · **Effort:** 1–2 d

### Problem
`npm run lint` is `eslint src --ext .ts,.tsx` but **no ESLint config exists** (verified: no
`.eslintrc*`, no `eslint.config.*`, no `eslintConfig` in `package.json`) — the linter has never run,
yet `CONTRIBUTING.md` tells contributors to run it and there are ~48 `eslint-disable` comments for a
linter that can't run. No Prettier, no husky, no lint-staged, **no secret scanning anywhere** — the
exact control that would have caught the P0 key leak.

### Fix
1. Add `eslint.config.js` (flat config) with `@typescript-eslint`. Start lenient (the codebase has
   ~1,700 `: any`): enable the high-value rules (no-floating-promises, no-unused-vars, no-console
   scoped to `src/main`+`src/renderer`) and set `@typescript-eslint/no-explicit-any` to `warn`.
   Run `eslint src` and either fix or `--max-warnings` at the current count as a ratchet baseline.
2. Add **gitleaks**: a `.gitleaks.toml`, a `secret-scan` CI job (`gitleaks detect`), and a
   pre-commit hook (husky + lint-staged, or a lightweight `.githooks/pre-commit`) running gitleaks +
   `eslint --fix` + `prettier --write` on staged files.
3. Add a `checkSensitiveData()` step to `scripts/package-addon.js` that scans the staged artifact for
   `sk-ant-`, `sk-[A-Za-z0-9]{48}`, `AIza…`, PEM private-key headers, etc., and **fails the package**
   on a hit.

### Acceptance criteria
- [ ] `npm run lint` runs to completion (0 errors; warnings baselined).
- [ ] gitleaks runs in CI on push/PR and as a pre-commit hook; a planted test secret is caught.
- [ ] `node scripts/package-addon.js` aborts when a fake `sk-ant-…` is present in the staging dir.

### Tests
- A gitleaks fixture (a dummy secret in a temp file) that the CI/hook flags.
- A packaging unit/smoke test: seed a fake secret into staging → `checkSensitiveData` throws.

## P1-1 — CI gate: lint + typecheck + jest on PR, required before publish

**Labels:** `ci` `high` · **Depends on:** P1-2 · **Effort:** 1 d

### Problem
`.github/workflows/` is only `docs.yml` + `package.yml`; **no workflow runs tests, lint, or
typecheck.** `package.yml` triggers on `v*` tags and publishes to R2/npm with no quality gate, so a
tag ships untested. The ~444 fast, fully-mocked `tests/unit`+`tests/main` files are green only from a
memory of a manual local run.

### Fix
1. Add `.github/workflows/ci.yml` on `push`/`pull_request`: `npm ci` → parallel jobs `lint`,
   `typecheck` (`tsc --noEmit`), `test` (`npx jest tests/unit tests/main`). No Local, no native
   Electron rebuild needed — `npm ci` compiles better-sqlite3 for system Node and the mocked suite
   runs in ~1–2 min.
2. Gate `package.yml`: make the publish job `needs:` a required CI run (or add the same
   lint+typecheck+test steps as a prerequisite job before Package/Upload), so a tag cannot ship red.
3. (Optional, follow-on) schedule the heavier tiers (`tests/integration`) nightly using the R2 model
   cache the packaging job already has.

### Acceptance criteria
- [ ] A PR with a failing unit test shows a red required check and cannot merge.
- [ ] A `v*` tag does not publish if lint/typecheck/test fail.
- [ ] CI wall-clock for the PR gate is under ~3 min.

### Note
Pin the known-pre-existing failing suites out (or fix them) first — baseline is currently 10 suites /
21 tests failing on native-module/model-dependent suites; the PR gate must run a **green** subset or
those get fixed as part of this ticket so the gate is trustworthy.

## P1-4 — `scripts/patch-node-abi.js` wired into `rebuild`; fix `NATIVE_MODULES.md`

**Labels:** `build` `dx` `high` · **Effort:** 0.5 d

### Problem
A fresh clone **cannot build the addon for Local**: `npm run rebuild` errors on the unknown Electron
42.2.0 ABI until two `node_modules/node-abi/abi_registry.json` files are hand-patched — a step
recorded **only in CLAUDE.md** and wiped by any `npm install`. And every version in
`NATIVE_MODULES.md` is wrong (verified): it says better-sqlite3 **11.10.0** (real: 12.11.1),
electron-rebuild **37.8.0** (real: 42.2.0), MODULE_VERSION **136/127** (Electron is 146; jest needs
141). A developer "fixing" the version to match the doc breaks the build.

### Fix
1. Commit `scripts/patch-node-abi.js` (the CLAUDE.md one-liner, made idempotent) that adds the
   Electron 42.2.0 entry with `"future": true` to both registry files.
2. Change the `rebuild` script to `node scripts/patch-node-abi.js && electron-rebuild -v 42.2.0 -f -w
   better-sqlite3` so it self-heals after any install. (Do **not** add a `postinstall` — that breaks
   shell `npm install`, per CLAUDE.md.)
3. Rewrite `NATIVE_MODULES.md`: correct the version table (12.11.1 / Electron 42.2.0 / ABI 146 for
   Local, ABI 141 for the jest system Node), paste the `NODE_MODULE_VERSION 146` error string so it's
   searchable, and replace the misleading `rm -rf node_modules` troubleshooting.

### Acceptance criteria
- [ ] `rm -rf node_modules && npm install && npm run rebuild` succeeds from a clean clone.
- [ ] `NATIVE_MODULES.md` versions match `package.json` and the actual ABIs.

## P1-5 — Harden the AI-gateway server

**Labels:** `security` `medium` · **Effort:** 0.5 d

### Problem
`HttpEventInterface.ts:177` sets `Access-Control-Allow-Origin: *` and validates no `Host`/`Origin`
header; `handleModels` (`AIGatewayRoutes.ts:400`) is dispatched with **no** `authenticateRequest`
call (unlike chat/images at `:157`/`:302`), so `GET /ai-gateway/v1/models` and `/health` are
unauthenticated. A web page the user visits can reach `127.0.0.1` via DNS rebinding and read the
configured provider and which keys are present.

### Fix
1. Validate the `Host` header against `127.0.0.1`/`localhost` (+ expected port) in the request
   handler; reject others (anti-DNS-rebinding).
2. Drop `Access-Control-Allow-Origin: *` — remove CORS or use an explicit allowlist.
3. Require auth on `/ai-gateway/v1/models` (call `authenticateRequest` in `handleModels`).

### Acceptance criteria
- [ ] A request with a non-local `Host` header is rejected.
- [ ] `/models` returns 401 without a valid token.
- [ ] No wildcard CORS header on gateway responses.

### Tests
- Unit tests over the request handler: rebinding `Host` rejected; `/models` unauthenticated → 401;
  authenticated → 200.

## P1-6 — Redact PII on the outbound-to-LLM path

**Labels:** `security` `privacy` `high` · **Effort:** 1–2 d

### Problem
There is **no PII minimization on the path to the cloud LLM** (the audit redactor is inbound-to-disk
only). `fleet_sql` (`fleet-sql.ts` — verified it returns `admin_email`/`users.email`), `wp_user_list`
(parse-failure fallback dumps raw `user_email`), and `wpe_get_account_users` hand fleet-wide admin and
user emails straight into the model's context. Combined with prompt-injection from indexed content,
this is a bulk email-exfiltration channel.

### Fix
1. Add an **outbound PII scrubber** (distinct from the audit redactor) that masks email/IP shapes,
   applied to tool *results* before they enter the model context, at the provider-client boundary.
2. Treat `admin_email`/`users.email` as restricted columns in `fleet_sql` output (mask, or require an
   explicit opt-in); never fall back to raw stdout in `wp_user_list` (return a generic error on parse
   failure); mask emails in `wpe_get_account_users` results.

### Acceptance criteria
- [ ] A `fleet_sql` query selecting `email` returns masked values by default.
- [ ] `wp_user_list`'s parse-failure path never emits raw `user_email`.
- [ ] The scrubber masks email/IP in an arbitrary tool result string.

### Tests
- Unit: the scrubber masks emails/IPs in representative tool-result payloads (must-mask corpus) and
  leaves non-PII intact (must-survive corpus) — mirror the audit test's both-direction corpus.

## P1-7 — `nexus creds rotate` + credential-rotation runbook + wire `recordError`

**Labels:** `security` `incident-response` `high` · **Effort:** 3–5 d

### Problem
Rotating a provider key today updates the **vault only** — the old key stays live in every managed
site's `wp_options` (synced there as plaintext by `setup-ai.ts`) and in every MU-plugin config; the
webhook token's `revokeSiteToken()` has no caller. Rotation is impossible to do correctly by hand.
Separately, `CloudflareTransmitter.recordError` exists (`:300`) with **zero callers** — failures are
invisible to the maintainer (usage-only telemetry).

### Fix
1. Build `nexus creds rotate <provider>`: overwrite the vault, then walk `sites` re-syncing/clearing
   the provider-key `wp_option` on each managed site, regenerate the webhook token, and re-push
   MU-plugin configs. Audit the rotation.
2. Write a **credential-rotation runbook** (extend `SECURITY.md` or a new `docs/incident-response.md`)
   enumerating every cache location a leaked key touches (vault, per-site `wp_option`, MU-plugin
   config, connection-info files).
3. Wire `recordError()` into both audit chokepoints (`ToolRegistry.call`, `auditDirectOperation`) —
   category-only, no payloads (the redaction machinery already exists) — so failures surface.
4. Surface the KeyVault plaintext-fallback state as a `nexus doctor` warning.

### Acceptance criteria
- [ ] `nexus creds rotate` invalidates a key everywhere it is cached (vault + N site `wp_option`s +
      MU configs + webhook token), verified against a test fleet.
- [ ] `recordError` fires on a failed tool call and is visible in telemetry.
- [ ] Runbook lists every credential cache location.
