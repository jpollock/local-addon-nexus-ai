## Workstream 1b — A0: the plugin audit reports non-updates as updates

*Reported by another session, **independently re-verified in source here**
2026-08-25. Promoted to the top of the queue: it is small, and it is the one
number in this list a person acts on.*

`WordPressOrgClient.checkUpdates()` (`src/main/resolver/WordPressOrgClient.ts:33`)
gates on truthiness — `if (info.new_version)` — and never compares the returned
version to the installed one. WordPress.org's update-check endpoint returns
entries whose `new_version` **equals** or is **lower than** the version
submitted, and every one becomes an "available update". Both consumers take the
map at face value (`SiteDataResolver.ts:115`, `plugin-audit.ts:45`), so a fully
current site reads as "4 updates available" — which discredits every other
figure printed beside it.

Measured by the reporting session across 42 local sites: 175 reported, ~95
genuine, **78 equal-version, 2 downgrades** — 46% false.

**Fix:** compare before reporting, reusing `compareVersions`
(`src/main/mcp/modules/fleet/version-utils.ts:19`) rather than writing a second
comparator — this repo has documented drift from duplicated rules, and today
that function exists in exactly one place. Report only `installed < latest`.
Withhold rather than guess on unparseable versions (`6.8.0-beta2` is live on
this fleet) and on `'unknown'` installed versions — an invented update IS the
bug.

**Verified additions to the brief:**
- The test gap is real and is why this shipped: `tests/unit/resolver/WordPressOrgClient.test.ts`
  has four cases and all four pass with the bug present — the "newer version"
  case submits `3.21.0` against `3.22.0`, so nothing exercises equal-or-lower.
  The new test must fail first.
- **`bulk_plugin_update` does NOT inherit these counts** (the brief flagged this
  as unchecked): it takes a caller-supplied `pluginSlug` and runs WP-CLI
  (`BulkOperationManager.executePluginUpdate`), and WP-CLI no-ops a current
  plugin. The exposure is indirect — a person or agent reading the false audit
  chooses to run updates that do nothing — not an automatic fleet-wide no-op.
- Secondary, **separate pass**: `WordPressOrgClient.ts:12` fabricates the plugin
  path as `slug/slug.php`. ACF PRO actually lives at
  `advanced-custom-fields-pro/acf.php`, so a mismatched path can resolve to a
  different plugin on wp.org — the likeliest explanation for the two
  downgrades. The comparison guard fixes the visible symptom either way; do not
  bundle the two.
**A0b — the fabricated path, fixed by checking identity (done).** The real
plugin file path is not available to send: the graph's `plugins` table has no
file column and `slug` is WP-CLI's directory name, so a true path needs a
column, a migration and every writer — its own change. What closes the defect
instead is reading the answer: wp.org states its own `slug` for whatever it
matched, and an answer about a different plugin is now discarded rather than
compared. This is the case A0's version check could never catch, because a
wrong plugin's version is usually genuinely higher. Absence of the field is
not treated as a mismatch — withholding on absence would stop reporting real
updates, the opposite failure.
**Residual, recorded not hidden:** we still send a guessed filename, so a
mismatch that wp.org answers WITHOUT a slug field would pass. Storing the real
path remains the complete fix and is Tier-C-sized.

- Non-goal: leave the live WP-CLI path alone — `wp plugin update --all
  --dry-run` is already filtered by WP-CLI.
