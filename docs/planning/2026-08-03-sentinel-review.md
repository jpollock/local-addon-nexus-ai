# Security Sentinel — Review

A full review of `agents/security-sentinel/` (agent.js 3,362 lines, five specialists, manifest, README) plus the runtime and UI it depends on — read as a single-user prototype for exploring agentic security analysis, running inside Local today, with an eye toward Atlas later.

## Verdict

The core problem is architectural, not a bug list: the sandbox is being used as the *detection* substrate when its only defensible job is the *remediation* workspace, and that one inversion is upstream of most of the critical findings below. Everything expensive, dangerous and unportable in this agent — pulling production files and databases to disk, detonating attacker mu-plugins on the user's machine, unbounded sandbox accumulation, the 100% Atlas-incompatibility of Tier 2 and Tier 3 — follows from it. Meanwhile the tier the target architecture actually wants already exists and works: Tier 1 is cheap, deterministic, fleet-wide, needs no sandbox, and is already remote-capable — it is just too thin to support the word "clean" (agent.js:420-422 emits a clean verdict having read nothing but cached plugin and user rows). As a forensic kit for a site you already suspect it is genuinely good, and the deliberate security work — the untrusted-data envelope in `specialists/_shared.js:13-47`, `phpJson()` at agent.js:24-36, derived remediation coverage at agent.js:3300-3311 — is better than most production security tooling. As an assurance tool it currently teaches the wrong lesson, because the parts that look finished (a clean verdict, a green approval screen, a cadence dropdown, a "READY TO PUSH" banner) are the parts least connected to what the code does.

## What's genuinely good

Concrete things a rewrite must not throw away.

- **The untrusted-data boundary** — `specialists/_shared.js:13-47`. Delimiter neutralization on the way in, a standing rule that nothing inside the markers can change task/schema/severity, and the instruction to treat an injection attempt as itself a CRITICAL finding rather than a reason to revise a conclusion. This belongs in the Nexus agent SDK as a shared primitive.
- **Structural, not prompt-based, containment** — `AgentAIClient.ts:105-118`. `noTools:true` passes only the synthetic `__output__` tool to the provider, so specialists structurally cannot call a site tool.
- **`phpJson()`** — agent.js:24-36. Closes a real code-execution class (attacker-controlled filenames re-entering PHP double-quoted-string interpolation inside `wp_eval`) with base64 transport, and the comment explains why `JSON.stringify` was not enough. Applied consistently at every remediation call site (2786, 2842, 2867, 2949, 2971, 3015) with `realpath()` containment at 2957, 2979, 3023.
- **Derived remediation coverage** — agent.js:3292-3311. The push verdict is computed from `SIGNAL_REMEDIATION_STEP` intersected with steps actually built and actually passed, not a hand-maintained boolean, so an unmapped critical structurally cannot yield READY TO PUSH. Right shape for a propose/apply model.
- **Remediation targets are deterministic** — agent.js:2545-2549. An LLM signal can *gate* whether a step runs but cannot choose its targets, and the comment records the bug that taught this.
- **Disciplined false-positive suppression written before the false positives** — `specialists/behavioral.js:74-97` ("nonces, cache-busters, rotating ads are NOT cloaking"), and sampling limits computed in JS rather than asked of the model (agent.js:1171-1186).
- **`parseSqlResult` warns instead of silently dropping** — agent.js:133-141, with the reasoning ("a malicious plugin whose name contains `|` would vanish from the scan") written at the point of the tradeoff.
- **FS-MISMATCH** — agent.js:2133-2156. Deliberately runs *with* plugins loaded to catch an account-hiding hook, in a file where everything else carefully skips them, and says why.
- **Account remediation never deletes** — agent.js:2756-2758. Disable and demote, preserving the forensic record and keeping every action reversible before push.
- **A working in-repo template for what is missing** — `agents/log-processor/` has per-site opt-in enrollment (`agent.ts:410`), an explicit budget (`agent.ts:20`), and a real SQLite schema with an `evict()` retention function (`db.ts:32-59`). The sentinel needs all three and invented none of them.

## Decision forks

These are the choices only you can make. Each states what the code does today, the alternative, the tradeoff both ways, and a recommendation.

### Fork 1 — Is the sandbox a detection substrate or a remediation workspace?

**Today.** Every Tier 2 check runs `wp_eval` against a full local clone (agent.js:1812-2442). For a WP Engine install that means `local_create_site` plus `local_wpe_pull({include_database:true})` — full rsync of `wp-content` plus a full database dump (`wpe-pull.ts:158-163`) — before a single byte is examined. Detection therefore requires a pull; remediation happens to reuse the same sandbox.

**Alternative.** Make detection remote and read-only. Every Tier 2 check is either a filesystem walk or a `$wpdb` read; both are executable over the SSH transport that already exists (`SentinelExecutor.ts:18-52` already runs raw SSH and SSH WP-CLI against production installs). Create the sandbox only after a human says "remediate."

**Tradeoff.** Against: read-only remote execution over SSH is slower per check than a local site, you lose the ability to re-run a check later against a frozen copy unless you snapshot deliberately, and `wpe_allowed_environments` currently excludes production for SSH/WP-CLI by default, so the guardrail has to be consciously widened for read-only operations. For: it collapses six of the most severe findings in this review into one refactor — SEC-01 (mu-plugin detonation on the user's machine), SEC-05 and SCALE-01 (unbounded sandbox accumulation), FEAT-09 (evidence destroyed before it is examined), SEC-02 (a hardening layer that only exists because malware is being executed locally), FEAT-02 (clean-verdict blindness, because the checks become cheap enough to run fleet-wide) — and it is the only path that makes Tier 2 portable to Atlas.

**Recommendation.** Do this. It is the headline. Five separate dimensions of this review arrived at it independently and none of them named it as one decision. Note the sequencing consequence: it also removes the need to answer the SEC-02 versus HARDEN-01 contradiction below, because a read-only remote check never needs `disable_functions` at all.

### Fork 2 — Sandbox lifecycle: four options

**Today.** Sandboxes are named `sentinel-<install>-<Date.now()>` (agent.js:1669), never deleted (`local_delete_site` is not in the agent's tool list at agent.js:321-328, so the agent structurally cannot remove what it creates), the 24-hour dedup cooldown is commented out (agent.js:1659-1667, "DEV MODE"), and `ipc-handlers.ts:4854` carries an unremoved TODO for the deletion that agent.js:2592-2593 falsely claims is handled. Thirteen of them are on disk right now, 92–202 MB each, containing live webshells and Linux ELF binaries in `~/PW-Local-Functional-Sites/`. You have said sandboxes are evidence; retention is the right instinct, but "retained" and "unmanaged" are different things, and today they are also *running* (PHP-FPM plus MySQL per sandbox).

- **Option A — Name and surface.** Rename to `sentinel-<install>-<YYYYMMDD-HHMM>` so sandboxes sort and match the report filename, and add a Sandboxes list to the agent workspace showing install, age, disk size, linked report, and a Delete button. *For:* zero risk of losing evidence, fixes the indexing problem (today a sandbox cannot be mapped back to its report without grepping every report), and is a prerequisite for B, C and D — you cannot retain-by-policy what you cannot identify. *Against:* does not stop accumulation, only makes it legible.
- **Option B — Ring buffer / keep-N-per-install.** Retain the most recent N (say 3) per install, evict the oldest on creation, mirroring the `pruneOldFiles(..., 20)` pattern already in `buildAgentContext.ts:97-98`. *For:* hard disk bound by construction, ~20 lines, survives the cron-with-no-cooldown case without any policy judgement. *Against:* a bad night evicts the case you cared about; eviction has no relationship to how interesting a case is.
- **Option C — Stop but retain.** Add `local_stop_site` to the tool list and stop the sandbox after the scan. *For:* removes process, port and memory cost immediately and independently of the disk question; one line of tool list plus one call. *Against:* disk still unbounded.
- **Option D — Evidence bundle, then release.** At the end of Tier 2, export the flagged files, the referenced database rows, the raw specialist inputs and the report into `reports/<install>/<ts>-evidence/` (or a 0600 tarball), then delete the Local site. *For:* highest fidelity per byte, bounded, portable, and the **only** option that survives a move to Atlas — a Local site is not a portable artifact, an evidence bundle is. *Against:* forces you to decide up front what counts as evidence, which is exactly what a sandbox exists to avoid; most new code.

**Recommendation.** A first, then C, then B as a backstop; D once A has told you which evidence you actually reach for. For a single expert exploring, the thing that hurts is a disk of indistinguishable `sentinel-*` sites, not the bytes — A is the cheapest change with the highest comprehension payoff. C is nearly free and removes the running-process cost that nobody has counted. Independently of the option chosen: re-enable the cooldown (agent.js:1667) keyed on install *plus signal fingerprint* so re-escalation happens when the evidence changes rather than on a timer, and gate it behind a `devMode` setting rather than a comment. Under Fork 1 this whole question shrinks dramatically, because sandboxes would only be minted when a human asks for remediation.

### Fork 3 — What belongs in the cheap deterministic tier

**Today.** Tier 1 reads cached `plugins` and `users` rows plus `settings_json` from graph.db and optional log aggregates. It has no content signal that can fire on its own, three of its config checks are broken or inert (SCALE-05), and two of its highest-severity checks are guesses (EXP-01 asserts REST user enumeration without measuring it; ABS-07 detects short plugin slugs rather than low-entropy ones).

**Alternative.** Move into Tier 1 everything that is cheap, deterministic, remote-capable and fleet-wide, and stop paying for a sandbox to learn it:

| Candidate | Cost | Why it belongs |
|---|---|---|
| Plugin/core version versus advisory feed (ABS-10) | one cached feed, one query | Vulnerable/outdated plugins are the most common real entry vector and have **zero** detection surface today (FEAT-01) |
| Abandoned/removed-from-directory plugins (ABS-11) | wp.org API, cacheable | The checksum 404 path already exists at agent.js:2397-2401 and is discarded |
| WPE SSH keys and portal users, baseline-diffed | two CAPI calls | The only layer where stolen hosting credentials show (FEAT-07) |
| The six behavioral `fetch()` probes | six HTTP requests | Turns EXP-01 from an inference into a measurement, and gives xmlrpc and cloaking ground truth for free (FEAT-05, SCALE-11) |
| FS-04 (PHP in uploads), CHK-01 (core checksums), DB-02 (autoloaded options) over read-only SSH | three `wp eval` round-trips per site | The three highest-yield content signals; without at least one, "clean" means nothing (FEAT-02) |
| `.user.ini` and web-served secret shapes (`wp-config.*`, `*.sql`, `.env`, `.git/`) | one directory read | WPE serves nginx; FS-05's `.htaccess` walk is inert on the target platform while `.user.ini` is unchecked (FEAT-11) |
| Cron hook orphan diff (DB-05) | one option read plus a set diff | Cron persistence is currently "covered" only by an LLM handed a 100-character slice of a multi-kilobyte option (FEAT-08) |
| Data staleness (STALE-01) | free | More valuable than most ABS checks: it is the signal that says the verdict is worthless (FEAT-03) |

**Tradeoff.** Promoting the HTTP probes generates outbound traffic to production sites on the fleet-wide path — a real change in blast radius, and **SEC-12 must be fixed first** because the URL is unconditionally `https://<install.name>.wpengine.com`, so promoting as-is would send Googlebot-spoofed traffic to *third-party* production sites every fifteen minutes. Read-only SSH checks require widening `wpeAllowedEnvironments` for reads. Against all of that: this is the tier that decides whether the tool can ever support the sentence "my sites have not been hacked," and every item above is cheaper than one sandbox pull.

**Recommendation.** Take the version/advisory check and the staleness signal first — they are pure data, need no transport work, and close the two largest blind spots. Then the account-layer checks. Then the read-only SSH content trio, which is where Fork 1 lands anyway.

### Fork 4 — The remediation model: replay-over-SSH versus fix-then-push

**Today.** Nothing in this system fixes a local copy and pushes it up. `local_wpe_push` is declared (agent.js:324, nexus.agent.yaml:27) and never called. The sandbox is a rehearsal stage whose *command strings* are collected by `generateCommands` (`AgentConsoleTab.tsx:179-199`) and replayed over raw SSH against production (`SentinelExecutor.ts:18-52`). The verdict says "READY TO PUSH" (agent.js:3314) about an artifact that never ships, and the UI says "Verified on isolated local sandbox" (`SentinelReviewOverlay.tsx:263`).

**Alternative.** Either (a) commit to replay-over-SSH and rename everything so it says what it means, or (b) actually implement fix-then-push, where the sandbox's end state is the artifact and `local_wpe_push` ships it.

**Tradeoff.** Replay is what exists and is simpler, but the verification proves less than the UI claims: it proves the commands are syntactically viable in a different environment, not that they produce the same end state on production — and today the production command set can diverge from the verified checklist in three concrete ways (SEC-03). Fix-then-push is your stated preference and gives a genuinely verified artifact, but it means pushing `wp-config.php` and every other mutated file, which is a much larger blast radius, and it needs an answer to an open question: **it is UNKNOWN from this repo whether Local's push includes `wp-config.php`** (`wpe-push.ts:128` delegates into flywheel-local). If it does, today's sandbox hardening would silently ship `WP_HTTP_BLOCK_EXTERNAL` to production and kill every outbound HTTP call — updates, payment gateways, transactional mail.

**Recommendation.** Pick (a) now and write it down in one paragraph at the top of agent.js, because the current state is the worst of both: a push-shaped vocabulary over a replay-shaped mechanism. Rename the verdict to "COMMANDS VERIFIED IN SANDBOX," delete `local_wpe_push` from the tool list, delete the hardcoded fallback command list at `AgentConsoleTab.tsx:202-219`, and make the executed commands derived from the verified checklist rather than hand-written parallel strings. Revisit (b) only after Fork 1, when the sandbox exists solely for remediation and its end state is the only thing it is for.

### Fork 5 — Trigger scope: fleet-wide versus saved group

**Today.** `nexus.agent.yaml:68` declares `scope: fleet`; the site query (agent.js:60-70) selects every row with `source IN ('wpe','local')` with no group predicate; `getScanScope` (agent.js:151-160) narrows only on `wpe:sync.completed`, so the `*/15` cron, `wp:plugin.activated` and `wp:user.created` all sweep the entire fleet. Activating any plugin on any local site fires a fleet sweep — and plugin activation is exactly what REL-02 detects, so the triggering event guarantees a signal.

**Alternative.** Scope to a saved group. Two places it could live: **in the agent** (a state key listing enrolled installs, mirroring log-processor's `getEnabledSites` at `agent.ts:410` — fastest, no SDK change) or **in the SDK trigger definition** (`EventTrigger.filter` is already declared at `types.ts:6-10` and read nowhere; a `scope: {group}` on CronTrigger would be the reusable primitive).

**Tradeoff.** Group scoping means a compromised site outside the group is never swept. Pair it with a slower fleet-wide cadence (daily) for everything else. Also confirm before designing on it: `list_site_groups` resolves member IDs against `services.siteData.getSites()`, i.e. **Local** sites — "a saved group of WPE installs" may not be expressible yet.

**Recommendation.** Build it in the SDK. Every future fleet agent will want the same thing, and `filter` being declared-but-inert is worse than absent — a reader of `types.ts` would reasonably believe scoping exists. In the meantime, scope `wp:plugin.activated` and `wp:user.created` to the emitting site via `getScanScope`, or drop them; an unscoped fleet sweep is the wrong response to a single-site event.

### Fork 6 — How far to unwind the Local coupling for Atlas

**Today.** Tier 1 is already portable: `collectFleetData` (agent.js:44-121) uses only `fleet_sql`, `wpe_site_deep_refresh` and `get_log_aggregates`. Tier 2 and Tier 3 are 100% unportable: every check and every remediation step runs through `wp_eval`, documented "LOCAL SITES ONLY — blocked on remote WPE installs" (`eval.ts:17`), and seven of sixteen declared tools are `local_*`. The least portable line in the agent is agent.js:1760-1768, which `require('fs')` inside agent code and appends to Local's `php.ini` on a path returned by `wp_eval` — the agent reaching around the tool layer into the host filesystem, so it would not even appear in a tool-availability audit. Report and evidence paths are hardcoded to `~/Library/Application Support/Local/...` in four independent places (agent.js:226-229, agent.js:3201-3205, `ipc-handlers.ts:4926-4931`, `ipc-handlers.ts:4900-4904`).

**Alternative.** Two SDK additions make this tractable without rewriting the agent: an **execution-environment abstraction** (`ctx.env.exec(target, code, {skipPlugins, skipThemes})` with a Local implementation today and a container/Atlas implementation later, so the ~40 `wp_eval` call sites move once) and **`ctx.paths`** for logs, reports and evidence so no agent hardcodes a macOS path.

**Tradeoff.** The abstraction is real work and premature if Atlas never happens. Against that: Fork 1 already requires a second execution backend (read-only over SSH), so you get the abstraction for free by doing the thing you want to do anyway, and the environment abstraction and the sandbox lifecycle (Fork 2) are the same primitive seen from two angles.

**Recommendation.** Do the path abstraction now — it is small, it is the second SDK change this review recommends regardless of the sentinel's fate, and four hand-built copies of one path is how a report ends up written somewhere `get-report` does not look. Defer the execution abstraction until Fork 1 forces it, then define its interface in terms of what Tier 2 needs ("give me something I can run read-only PHP against, seeded from install X") rather than in terms of Local's site lifecycle.

### Fork 7 — The hardening contradiction (SEC-02 versus HARDEN-01)

Two findings in this review recommend opposite fixes and both are defensible. SEC-02 says make `disable_functions` assertable and hard-abort Tier 2 when the probe fails. HARDEN-01 says drop `shell_exec` from the disable list, because CHK-01's core verification (agent.js:1050), the ELF `strings` analysis (agent.js:1494) and the salt shuffle (agent.js:3038) all depend on it, as do four `wp_remote_get` call sites that need curl or fsockopen. Empirically both states have occurred on your machine: `agents/security-sentinel/logs/agent.log` shows ten hardening failures on 2026-07-19 followed by full unhardened scans, and no `php.ini` under Local contains the sentinel's marker.

**My read: neither rec is right, and the correct answer is stated in neither.** Move the checks that need network or shell **out of the sandbox PHP** — checksum fetch, SVN diff and `strings` all belong in Node, where the agent controls the request; the salt shuffle is a `wp-config` rewrite that needs no shell. Then hardening can be strict *and* assertable without disarming anything, and `allow_url_fopen=Off` should be added since `disable_functions` does not cover URL wrappers, `mail()` or `pcntl_exec`. Under Fork 1 this fork disappears entirely.

## Suggested sequencing

You asked to stop at findings, so this is order-of-operations reasoning, not a plan.

- **Decide Fork 1 before fixing anything downstream of it.** Roughly a third of the critical and high findings — SEC-01, SEC-02, SEC-05, SCALE-01, FEAT-09, FEAT-12, ATLAS-01, and Fork 7 entirely — either disappear or change shape depending on whether detection stops using the sandbox. Fixing them individually first means fixing code that would then be deleted.
- **The lies are cheap and should not wait on any fork.** UX-01, UX-03, UX-04/LOG-05, SANDBOX-01, UX-02, VERIFY-01, SDK-01, SDK-02 are all trivial-to-small and every one of them currently tells you something false about cost, safety or outcome. They are independent of the architecture and they are what makes the prototype trustworthy enough to iterate on.
- **Then the measurement gap, before tuning any detector.** LOG-13 (test harness accumulates findings), LOG-01 (findings history), LOG-09 (provenance), SCALE-08 (cost attribution). Without these you cannot tell whether a change to ABS-07's heuristic or the escalation threshold made anything better, which is the main thing this prototype is supposed to teach. Take the false-positive measurement immediately after.
- **Then thicken the cheap tier** (Fork 3), starting with the checks that need no new transport: plugin versions/advisories, staleness, account-layer diffs. This is where the product direction actually lives.
- **Documentation last but not never.** DOC-01 plus TAXONOMY-01 is roughly two hours and is the single highest-return item for the six-months-later test — but it should be written after the forks are decided, so it documents the architecture you chose rather than the one you are leaving.
